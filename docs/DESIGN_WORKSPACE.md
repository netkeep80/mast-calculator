# Отдельный модуль 3D и конструкторской документации

Статус: архитектура issue #47, prototype **1.5**.

## 1. Почему модуль выделен отдельно

До issue #47 конструкторская документация ЕСКД автоматически приклеивалась в конец бумажного расчётного проекта. Это смешивало два разных артефакта:

- **расчётный проект** объясняет физическую модель, нагрузки, FEM, соединения, верификацию и найденные пределы;
- **конструкторская документация** описывает уже принятую геометрию изделия для изготовления.

После рефакторинга `createCalculationProjectHtml()` больше не включает листы КД. Отдельная страница `apps/web/design.html` получает рассчитанную конструкцию и отвечает только за геометрию изделия, 3D, OBJ и КД.

## 2. Поток данных

```text
калькулятор
   ↓
FEM + соединения + подбор
   ↓
готовый calculation result
   ↓
buildDesignPackage()
   ↓
mast-calculator/design-package/v1
   ↓
localStorage / JSON-файл
   ↓
┌──────────────────────────────┐
│ design.html                  │
│                              │
│  MastViewer                  │
│  JointViewer                 │
│  createMastObj()             │
│  ESKD v2                     │
└──────────────────────────────┘
```

Отдельный модуль **не запускает второй FEM** и не пересчитывает конструкцию независимо. Он получает уже выбранную физическую конструкцию.

## 3. Design package

Схема:

```text
mast-calculator/design-package/v1
```

Пакет содержит только данные, необходимые для воспроизводимого представления изделия:

- `parameters` рассчитанной конструкции;
- `model.nodes`, `model.members`, `model.modules`;
- фактические диаметры members, включая mixed-diameter profile;
- выбранную геометрию межмодульного узла;
- минимальный набор utilization для окраски существующего 3D viewer;
- производственную оценку массы.

В пакет намеренно **не копируются** эксплуатационные wind cases, height search, полные FEM-матрицы и другие большие расчётные данные, которые не нужны для изготовления.

Пакет можно:

1. автоматически передать из калькулятора через `localStorage`;
2. скачать как JSON;
3. позже загрузить в `design.html` без повторного FEM.

## 4. Единая геометрия 3D и OBJ

Подробная модель мачты по-прежнему строится через:

```text
buildDetailedMastModel(result)
```

Схема модели:

```text
mast-calculator/detailed-mast-model/v1
```

Её используют:

- встроенный `MastViewer`;
- новый design workspace;
- Wavefront OBJ exporter.

Поэтому OBJ не содержит отдельную геометрию, независимую от экранного представления.

Соединительный узел в design workspace использует существующий `JointViewer` и `buildJointVisualGeometry()`, то есть те же две гайки, болт, 4+2 направления рёбер и сварочную зону, которые показываются в основном калькуляторе.

## 5. КД v2: чертёж строится из модели, а не рисуется вручную

Старая реализация ЕСКД вручную рисовала условные линии в SVG. Такая схема быстро расходится с реальной 3D-геометрией.

Новая схема:

```text
mast-calculator/eskd-construction-documentation/v2
```

Для видов мачты и модуля используется:

```text
mast-calculator/technical-projection/v1
```

`technical-projection.js` получает polygon mesh и автоматически строит:

- вид спереди;
- вид сверху;
- изометрическую проекцию;
- видимые/контурные рёбра;
- штриховые скрытые резкие рёбра;
- размерные линии.

Таким образом основные графические виды происходят из **той же detailed mesh**, что 3D/OBJ.

Для межмодульного узла геометрические размеры и 4+2 направления рёбер берутся из `buildJointVisualGeometry()`. Это исключает отдельный вручную поддерживаемый набор размеров узла внутри генератора КД.

## 6. Что видит пользователь

После обычного расчёта в строке экспорта появляется кнопка:

```text
Открыть 3D и КД
```

Старый прямой OBJ-экспорт из расчётного экрана убран из фокуса. В design workspace доступны четыре самостоятельных действия:

```text
Скачать пакет JSON
Скачать OBJ
Скачать КД по ЕСКД
Открыть пакет JSON
```

КД показывается в iframe-предпросмотре до скачивания.

## 7. Разделение ответственности

### Калькулятор

Отвечает за:

- исходные данные;
- нагрузки;
- FEM;
- устойчивость;
- болты/гайки/сварку;
- пределы;
- расчётный проект и верификацию.

### Design workspace

Отвечает за:

- подробную модель принятой конструкции;
- интерактивный просмотр;
- OBJ;
- переносимый JSON package;
- проект КД.

Это архитектурная граница. Нельзя возвращать КД в `fabrication-project-appendix.js` или расчётный HTML как скрытый appendix.

## 8. Нормативная граница

Автоматический экспорт остаётся **проектом КД**, а не подписанным подлинником.

Программа не имеет права автоматически придумывать:

- код организации-разработчика;
- уникальные обозначения;
- фамилии и подписи;
- технологические допуски;
- покрытие;
- технологию и контроль сварки;
- фактические паспортные размеры закупленных метизов.

Поэтому перед выпуском в производство нужны присвоение обозначений, заполнение основной надписи, технологическая проработка и нормоконтроль.

## 9. Regression contracts

`tests/design-workspace.test.js` проверяет:

- compact design package;
- JSON/localStorage round-trip;
- восстановление detailed mesh и OBJ без повторного FEM;
- наличие отдельной страницы с 3D, OBJ, JSON и КД;
- явную точку перехода из основного UI.

`tests/eskd-export.test.js` проверяет:

- ЕСКД v2;
- шесть листов A4;
- актуальные стандарты;
- projection contract из shared mesh;
- production hardware/assembly values;
- отсутствие фиктивных подписей/обозначений;
- принципиальное отсутствие КД в бумажном расчётном проекте.
