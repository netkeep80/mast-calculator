# Issue #36 — упрощение статической нагрузки и раскроя арматуры

Статус: проектный контракт PR по issue #36.

## Цель

Пользовательский интерфейс должен отвечать на два практических вопроса без дублирующих способов задания одной и той же нагрузки:

1. сколько суммарной массы можно разместить на верхней грани **вертикальной мачты** и сколько килограммов остаётся до первого расчётного предела;
2. какой максимальный концевой груз выдерживает та же конструкция, если её использовать **горизонтально как консольную стрелу**.

Поля «дополнительная вертикальная сила» и «дополнительная горизонтальная сила» не являются пользовательскими параметрами. Внутренние единичные/контрольные нагрузки передаются отдельным расчётным API и не попадают обратно в пользовательскую модель.

Эквивалентный объём воды не является отдельным structural result: при необходимости он непосредственно получается из массы и выбранной плотности.

## Вертикальная мачта

Единственная пользовательская вертикальная нагрузка вершины:

```text
equipmentMassKg
```

Gravity-only capacity возвращает:

```text
maximumTopEquipmentMassKg
configuredTopEquipmentMassKg
additionalTopEquipmentMassKg
```

Собственный вес мачты включён; wind/ice в специальной задаче отключены.

## Внутренний point-load API

Verification fixtures и normalized load cases используют:

```text
buildLoadCase(model, parameters, {
  topPointLoadN: [Fx,Fy,Fz]
})
```

Legacy `extraHorizontalLoadN`/`extraVerticalLoadN`, даже если присутствуют в старом объекте параметров, production load builder игнорирует.

## Две разные поперечные задачи

### Pure lateral reference

Существующий `lateralCapacity` остаётся нормированной проверкой:

```text
1 Н transverse
self weight = 0
wind = 0
ice = 0
equipment = 0
```

Он нужен для аналитических/regression checks и даёт чистый structural upper bound `Flim`.

### Horizontal boom capacity

Для практического вопроса issue #36 добавлен отдельный `craneBoomCapacity`.

Та же frame geometry используется горизонтально: вместо физического поворота модели вектор гравитации арматурных members поворачивается в горизонтальную плоскость. Поэтому собственный вес стрелы становится распределённой поперечной нагрузкой:

```text
qg = rho*A*g*gamma_g
```

Концевой груз:

```text
Pend = m*g*gamma_payload
```

Проверяются member, fixed physical joint/bolt и global buckling. Основной результат:

```text
maximumEndPayloadMassKg
```

Он обязан отличаться от простого `Flim/g`, поскольку расходует часть несущей способности на собственный вес горизонтальной стрелы.

Подробности: [`CRANE_BOOM_CAPACITY.md`](CRANE_BOOM_CAPACITY.md).

## Раскрой арматуры

Количество равных частей закупочного прутка поддерживается во всём диапазоне:

```text
1, 2, 3, …, 48
```

Количество частей остаётся целым положительным числом:

```text
a = Lstock/nparts
1 <= nparts <= 48
```

Валидация выполняется в расчётном каталоге, а не только в UI.

## Граница модели

Issue #36 упрощает пользовательскую модель нагрузки и терминологию, но не отменяет FEM, собственный вес, ветер, лёд, проверку соединительного узла, local/global buckling и коэффициенты надёжности.

Горизонтальная стрела пока учитывает собственный вес **арматурных frame members**, но не добавляет автоматически fabrication mass гаек/болтов/сварки в FEM. Также не моделируются динамика подъёма, рывок, трос/блоки/лебёдка, шарнир/поворотный узел, fatigue и специальные нормативные требования к грузоподъёмным механизмам. Поэтому результат является предварительной инженерной оценкой, а не паспортной SWL крана.
