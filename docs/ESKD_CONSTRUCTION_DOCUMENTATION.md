# Экспорт конструкторской документации по ЕСКД

Статус: отдельный design workspace, схема `mast-calculator/eskd-construction-documentation/v2`.

## Назначение

Конструкторская документация больше **не входит в бумажный расчётный проект**. Это принципиальная граница issue #47:

```text
расчётный проект = почему конструкция проходит расчёт
КД              = как выглядит и из чего изготовить принятую конструкцию
```

После расчёта основное приложение передаёт компактный `design package` в отдельную страницу `design.html`. Там пользователь видит подробную 3D-модель, может скачать OBJ и отдельный комплект КД.

Полная архитектура: [`DESIGN_WORKSPACE.md`](DESIGN_WORKSPACE.md).

## Нормативная база для РФ

Экспорт ориентирован на действующую в Российской Федерации систему ЕСКД:

- **ГОСТ Р 2.102-2023** — виды и комплектность конструкторских документов;
- **ГОСТ Р 2.104-2023** — основные надписи и дополнительные графы;
- **ГОСТ Р 2.105-2019** — общие требования к текстовым документам;
- **ГОСТ Р 2.109-2023** — основные требования к чертежам;
- **ГОСТ Р 2.201-2023** — обозначение изделий и конструкторских документов;
- **ГОСТ 2.301-68** — форматы листов.

Старые ГОСТ 2.102-2013 и ГОСТ 2.104-2006 не используются как основная нормативная база российского экспорта.

## Состав комплекта

Генератор создаёт шесть самостоятельных листов A4:

1. `Мачта модульная. Сборочный чертеж`;
2. `Мачта модульная. Спецификация`;
3. `Модуль мачты. Сборочный чертеж`;
4. `Модуль мачты. Спецификация`;
5. `Узел межмодульный. Сборочный чертеж`;
6. `Ребро. Чертеж детали`.

Графические листы получают основную надпись формы 1, спецификации — формы 2. HTML готов к `Ctrl+P → Сохранить как PDF` с форматом `@page A4`.

## Чем v2 отличается от старого экспорта

Первая реализация вручную рисовала в SVG условную мачту и условный модуль. Такая схема имела второй источник геометрии и закономерно выглядела как слабый эскиз.

В v2 виды мачты и модуля автоматически выводятся из:

```text
buildDetailedMastModel(result)
        ↓
technical-projection/v1
        ↓
front / top / isometric SVG
```

То есть чертёжная проекция, экранная подробная 3D-модель и OBJ имеют общий источник геометрии.

Алгоритм проекции выделяет контурные и резкие рёбра polygon mesh, различает видимые и скрытые линии и автоматически вписывает геометрию в область вида.

Для соединительного узла размеры и направления шести рёбер берутся из `buildJointVisualGeometry()`, который также обслуживает интерактивное окно узла.

## Single-source принцип

КД получает из рассчитанной конструкции:

- число модулей;
- фактические `model.nodes`/`model.members`;
- реальный диаметр каждого member, включая mixed-diameter profile;
- длину ребра и высоту модуля;
- класс арматуры;
- выбранный болт и его класс;
- проходную и длинную гайки;
- длину зацепления;
- катет и требуемую физическую длину сварного шва;
- сварочный материал;
- производственную оценку массы.

Никакого отдельного массива «размеров для чертежа» не поддерживается.

## Design package

Между расчётным приложением и модулем КД используется:

```text
mast-calculator/design-package/v1
```

Он достаточно компактен для `localStorage`, но также может быть скачан как JSON и открыт позднее. Пакет не содержит полного набора эксплуатационных load cases и не запускает повторный FEM.

## Почему обозначения и подписи не заполняются автоматически

ГОСТ Р 2.201-2023 требует реальной системы обозначений организации-разработчика. Калькулятор не знает код организации, утверждённую систему обозначений, ответственных лиц и их полномочия.

Поэтому генератор намеренно выводит:

- `Обозначение: НЕ ПРИСВОЕНО`;
- пустые поля `Разраб.`, `Провер.`, `Н. контр.`, `Утв.`;
- пустое поле организации-разработчика.

Перед выпуском в производство необходимо:

1. присвоить реальные обозначения;
2. заполнить реквизиты и подписи;
3. провести нормоконтроль;
4. назначить технологические допуски;
5. назначить защитное покрытие;
6. сверить фактические покупные метизы с документацией поставщика;
7. утвердить технологию и контроль сварки.

## Граница автоматизации

Экспорт является автоматически сформированным **проектом КД**, а не подписанным подлинником и не сертификацией изделия.

Программа не придумывает недостающие производственные решения. Наличие красивого чертежа не превращает расчётную модель в утверждённую рабочую документацию без инженерного и нормативного выпуска.

## Проверки

Основные contracts закреплены в:

```text
tests/eskd-export.test.js
tests/design-workspace.test.js
```

Проверяется в том числе отрицательное архитектурное требование: `createCalculationProjectHtml()` больше не должен содержать листы `eskd-sheet` или схему ЕСКД.

Локальная проверка:

```bash
npm run test:design
npm test
npm run check
```
